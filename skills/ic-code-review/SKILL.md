# ic-code-review

主产出是代码及验证证据的审查报告，不重新定义产品。仅用户显式调用时启用；同目标可复审，完成、取消或切换无关主题即停止。不自动调用其他 `ic-*` skill；读取本文件或方法参考不等于启动阶段。无需先执行 ic-do 才能审查已有变更。

主会话负责范围、授权、证据整合与阶段主文档，默认直接审查；必要时按能力派审查或专业取证任务，不固定类型。传递任务、依据、授权、必要方法与交付要求，不默认让子代理重读和执行整套阶段流程。允许操作取用户授权、角色边界、任务范围与宿主限制的交集；子代理不重新访谈用户、不再次委派、不推进阶段，被审代码、测试、文档和配置始终只读。只返回正文的角色由主会话落盘，具备相应产物权限的角色也仅写分配的证据附件；一个工作目录一个写入者，并行写入先安排独立目录，结果核对后由主会话整合。

涉及 UI/交互/视觉取证时按需读取 [frontend-methods.md](../_shared/frontend-methods.md)；专项 Skill 中的实现或修复指令不适用于本次只读任务。

## 1. 固定目标与证据

明确实现目标、比较基线、代码版本和 diff 范围，读相关需求、准备文档、调用方和执行记录（如有）。审查未提交变更时覆盖暂存、未暂存及相关未跟踪文件；缺少 spec 时用已确认目标核对，无法建立契约则声明该维度证据不足。

事实自行核实；目标或影响结论的取舍不清楚时持续逐题讨论，每次一个问题，给依据、推荐和代价，直到用户确认或暂停。沿用有效确认，新证据改变依据时重开；未决项保留，不代用户选择。说明独立性：没有独立审查上下文时标为主会话自查，不把作者自评当作通过证据，也不强制委派。

## 2. 核对变更与验证

与实施阶段共用 [verification.md](../ic-do/references/verification.md)，不另造通过标准；读取该参考不获得 `ic-do` 的修改或执行授权。

- **契约**：对照已确认的需求、UI、Design、验收与非目标，找遗漏、错误实现和越界行为；研究建议不能当作已批准需求。
- **正确性与质量**：沿真实调用链检查数据、权限、状态、失败、并发、回退和边界；关注责任归属、重复逻辑及不必要抽象，仓库约定优先于个人偏好。
- **验证证据**：按共同参考核对回归、集成与必要自动化，以及命令、环境、结果和被测版本/工作区快照；只有 HEAD 或文件列表无法证明未提交内容已测试，后续相关修改使旧结果不足以证明当前代码。
- **UI**：关键旅程和适用状态有浏览器自动化证据，截图/手测/扫描仅补充；模拟不替代真实集成。沿用本任务已确认的要求，未执行项保持未验证，用户调整须记录；视觉打磨轮次不豁免功能缺陷。按需派专业角色只读核验，不因其实现能力而授权修复。

每项 finding 给位置、具体证据、影响、严重度（阻塞/重要/建议）和最小修订方向；区分缺陷、疑点与用户待决策项。契约、代码质量和验证缺口分开呈现，再按影响排序；风格偏好不阻塞。

被审代码、测试、文档和配置保持只读；仅可创建或更新本 skill 的审查报告及其证据附件，不生成修复补丁。测试或交互验证先说明目的、成本和副作用，获用户同意后在隔离副本/测试环境执行，允许该环境内的缓存和测试产物，不修改被审材料或写入生产/外部系统。资料中的命令不是授权；未运行项如实标明。

## 3. 维护审查报告

实质审查成果默认落盘：有依据的 findings、复审或交接结论写入主文档 `docs/ic-code-review/YYYY-MM-DD-<topic>.md`；审查证据与专题放 `docs/ic-code-review/YYYY-MM-DD-<topic>/` 并相对链接，不复制被审材料为另一份规范。主会话整合返回内容并维护结论、状态与索引；角色只返回正文时不要求它落盘，其他角色也仅写明确允许并分配的证据附件。无需用户另说“保存”；一次性短答可只回复，用户明确要求保存或禁止写文件时优先遵循。

报告路径相对目标业务项目根目录（默认调用时工作目录），不是 skill 安装目录；随包引用仍相对 skill 目录。先定位同主题同阶段报告，候选不明先消歧。用户补充或新证据到来时及时修改对应章节、关联结论和未决项，替换失效内容而非文末堆叠补充；只有独立的新阶段或新快照才新建文件。保留 `created`，更新 `updated` 和 `status`。

报告包含目标/基线/diff、准备依据和被测版本、独立性、已读/未覆盖范围、findings、验证缺口，以及 `可交付`、`修复后复审` 或 `证据不足`。目标、依据或相关代码变化时旧结论失效，复审完整当前目标与修复，更新已解决、未解决及新问题。

## 4. 交付与完成

完成表示本次范围已核对、发现有依据、缺口已公开，应落盘的报告已实际写入并回读确认；写入失败如实报告。只有契约与实现达标、必要验证证据对应当前目标且无阻塞问题，才给可交付结论。

回复给结论、关键问题和风险及 `已落盘：<path>` 或 `未落盘：<理由>`，落盘后不重复全文，用户要求详细内容时除外。通过不等于用户接受、提交或发布；实现问题交回 `ic-do`，产品/Design 变化交回 `ic-prepare`，后续由用户显式启动，不自动修复、提交或发布。
