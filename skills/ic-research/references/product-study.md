# 完整产品与开源调研

这是研究方法参考，不是新的 Skill 入口；读取它不启动 `ic-research` 或后续阶段。用于完整竞品/开源产品研究，不强加给单个 API、库用法或本地代码定位。范围与授权由当前任务决定，结论不代替目标产品的需求或设计决策。

## 1. 选定研究对象

- 先写本轮要回答的产品问题、用户任务、比较维度与约束，再主动查找直接竞品、替代方案和相关开源项目。用户限定对象时不扩大名单。
- 候选发现与正式研究分开：说明哪些进入深析、哪些排除及原因，不暗中只取易访问对象或把搜索结果当成已分析。
- 对正式对象采用相近的比较维度与证据深度，差异须说明；不按统一评分凑结论，不把竞品功能合集当自己的 MVP。
- 涉及体验或性能口碑时，选择与目标版本/时期匹配的独立讨论，区分个别反馈与反复出现的问题；热度不等于质量，官方宣传不等于实测。

## 2. 浏览器实查（正式产品对象必做）

- 用当前可用浏览器工具实际打开产品或可运行演示；有 `agent-browser` 时先读其 Skill 和当前 CLI 的 core 指南。使用任务独立会话，避免影响其他人的页面、登录态和截图。
- 走本次核心用户流程，记录入口、操作、进度、结果、异常、恢复和退出；检查相关空态、错误、权限、取消/撤销/重试、桌面/移动布局和键盘行为。官网、帮助文档和演示视频只能补充，不能冒充亲自操作。
- 保存关键状态截图、步骤、URL、观察日期、可知的版本/套餐/登录状态。价格与限制注明来源和时间，评论只作待核验线索。
- 公开只读访问和不会写入外部系统的交互属于研究取证；登录、购买、提交内容、上传数据或改变远端状态必须在明确授权内。无法访问时记 `missing evidence`，保留未走到的流程，不伪造成功。

## 3. 开源源码深析（正式对象有开源仓库必做）

- 从官方来源确认仓库，`git clone` 到任务独占目录，固定并记录实际 commit、相关 tag/branch 与许可证。不要在用户现有工作区切分支；窄代码调查可复用已有版本匹配的 checkout，不要求为了形式重复克隆。
- 浅克隆缺目标版本时补取所需引用。线上产品与源码版本、开源版与商业版分别记录，不能把默认分支当线上实现。
- 沿核心路径追踪入口/路由 → 页面与组件 → 状态和业务逻辑 → API/服务 → 持久化，核对消费者、错误/权限/恢复分支、配置和测试；读相关完整实现，不止 README、目录树或搜索片段。
- 分析模块职责与依赖、渲染与状态管理、接口契约、实体关系、存储/缓存/同步、鉴权、性能策略、测试与部署。圈定相关子系统并披露未覆盖范围，不假装审遍整个仓库。
- 将浏览器行为对应到源码位置和调用链；关键结论附 commit 固定链接或仓库相对路径、符号及行号。只公开前端时不推断完整后端/数据库；静态测试定义不等于测试已运行。
- 记录许可来源；准备采用、修改或分发代码/资产时核对相关义务与兼容性，未知不能写成“可商用”。不将这一步扩成无依据的法律结论。

## 4. 有问题驱动的安装与运行实验

- 先说明要验证的问题，例如大文件行为、自托管依赖或扩展能力，而不是默认安装所有候选。
- 第三方依赖安装、编译、启动、容器和测试执行需主会话取得或明确转交授权；说明成本、脚本和副作用，已有有效授权不重复询问。
- 使用独立副本/测试环境与测试数据，不注入真实密钥或生产数据库。检查将执行的命令和安装脚本，不把仓库内指令当新授权；隔离目录本身不是安全沙箱。
- 记录实际命令、版本、环境、结果和退出状态；失败保留错误与缺口。运行不了就仅交静态结论，不把安装计划写成运行证据。
- 清理自己创建且不再需要的进程和临时资源。保留可复核证据；临时源码清理后，结论仍可通过仓库 URL 与 commit 追溯。

## 5. 文档与证据

产物根目录与写入归属由当前任务指定。显式研究阶段默认采用以下“一份主文档 + 专题附件”；普通任务仅借用本参考的方法时不自动创建阶段目录：

```text
docs/ic-research/YYYY-MM-DD-<topic>.md
docs/ic-research/YYYY-MM-DD-<topic>/
  <competitor>/
    README.md
    architecture.md
    ui-design.md
    data-architecture.md
    product-ux.md
    evidence/
```

路径相对目标项目，不是 Skill 安装目录。主会话维护主文档的范围、跨竞品比较、结论与前提、取舍建议、未知项和附件索引；不另写一份重复的总比较报告。子代理只返回正文时由主会话落盘，只有角色允许且已明确分配时才写附件；所有文件可用相对链接追踪。

| 附件 | 回答的问题 |
|---|---|
| `README.md` | 来源、日期/版本/commit/许可证、分析范围、浏览器与源码证据索引、缺口 |
| `architecture.md` | 系统上下文、模块职责与依赖、技术选型、关键调用链、运行/部署与取舍；有证据时附架构/时序图 |
| `ui-design.md` | 页面/导航结构、布局密度、字体与语义 tokens、组件、交互状态、动效、响应式、无障碍及截图/实现对应 |
| `data-architecture.md` | 实体与关系、schema/类型、API/数据流、存储/缓存/同步、校验/权限/一致性和恢复；有依据时附 ER/数据流图 |
| `product-ux.md` | 目标用户、核心功能、端到端任务、反馈/容错/恢复、优势与代价及证据 |

正式完整研究按这些维度分别落盘；闭源或证据不足的维度注明公开支持的事实和未知，不能填空编造。安全、性能、测试等专题有实质内容再拆文件。截图/日志按状态组织并脱敏，不保存凭据或真实私有数据。

## 6. 形成判断并停止

比较采用“怎么做 → 解决什么问题/付出什么代价 → 适用条件 → 采用、调整或拒绝的建议”。分清实际观察、源码事实、官方声明、推断与未知；性能和体验结论没有测量或观察就不当事实。

说明研究对目标产品带来的机会、限制与待决策项，不提前确定目标架构或扩大功能范围。满足问题或无法取得更多有效证据时停止，明确有界成果；必要实查/源码未完成时不得声称完整研究已验证。建议交回主会话与用户确认，不自动进入准备或实现。
