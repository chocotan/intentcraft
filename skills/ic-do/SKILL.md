# ic-do
按用户已授权的目标实施并用相称证据证明结果，不负责重新定义产品。仅用户显式调用时启用；同主题可继续，完成、取消或切换无关主题即停止。不自动调用其他 `ic-*` skill。

## 开工边界

优先读取已确认的 `ic-prepare` 计划、相关 `ic-design-review` / `ic-code-review` 报告（如有）和当前仓库事实，核对版本、范围、依赖、接口与授权。没有计划但目标简单清楚时，在回复中形成最小目标和验证口径；复杂目标缺少需求、设计或关键取舍时说明缺口并询问用户是补计划、调用 `ic-prepare` 还是缩小目标，未确认前不扩大实现。不修改用户未授权的产品范围、权限、公开契约、数据语义或部署策略。

先调查现有实现和调用方，复用正确归属的能力。按最小端到端路径实施，保持与计划一致；实现细节可自行决定，但产品行为、接口契约或验收变化必须暂停并交用户确认。发现新风险时补相称的验证，不用“改动很小”省略必要护栏。

## 测试与验证
- 非平凡逻辑（分支、循环、解析、状态、金额、权限、数据变换等）至少补一个会在行为回归时失败的单元或行为测试；优先使用现有测试设施。
- API、数据库、队列、外部依赖或跨模块数据流按需要补集成测试，验证真实边界；不可控外部依赖才可 mock。
- 有界面功能时，使用现有浏览器自动化设施验证关键用户旅程和会改变行为的状态，至少覆盖适用的成功、失败、加载、空、禁用、执行中或重试状态。截图只能补充视觉证据，不能替代交互验证。
- 纯文案、简单样式或显然等价的小改不强制新增完整测试，但仍运行最相关的现有检查；UI 样式改变影响布局、可用动作或视觉契约时，增加对应的浏览器或视觉检查。
- 未运行、工具不可用或只能手测的内容明确列为未验证，不声称通过。

## 产出契约

由 Agent 判断执行记录是否需要持久化，不以用户是否逐字说“保存”为唯一条件：包含非平凡实现、测试证据、风险、回退或后续交接价值时，默认落盘；一次性短答、局部探索或用户明确要求不写文件时，只在回复中交付。用户明确要求保存或不保存时优先遵循。每次明确说明 `已落盘：<path>` 或 `未落盘：<理由>`。

需要落盘时，只写入目标业务项目根目录下的 `docs/ic-do/YYYY-MM-DD-<topic>.md`；不写入 skill 安装目录。相对目标业务项目根目录解析，默认是调用时工作目录。同一实现阶段、用户补充或新测试结果出现时，定位并直接更新原文件对应章节，不机械地在结尾追加；新批次或范围变化才新建日期文件。多个匹配文档不按日期猜，先按路径、状态和引用消歧，无法确认就询问。执行记录只保留结果，不复制完整计划：

```text
实现目标与范围
实际改动与关键偏差
实现与测试对应的版本或工作区快照（commit、diff 或未提交状态）
测试/验证命令、场景与结果
UI 自动化或手测结果（如适用）
未验证项、风险与回退说明
后续建议
```

状态使用 `implemented-unverified`、`verified`、`blocked`；执行记录必须说明实现与测试对应的 commit、diff 或工作区快照，未提交改动需说明测试覆盖的文件范围；缺少必要证据或无法与当前版本对齐时不得标为 `verified`。实现和验证达到已授权目标才可报告完成；这不等于关闭、提交、发布或用户最终接受。默认不创建额外 issue 或设计文档，不自动 commit、push、部署或迁移。

## 发现偏差时

局部实现细节偏差可修正并记录；如果需求、UI 契约、公开接口、数据模型、权限、关键状态或验收发生变化，停止当前实现，交回 `ic-prepare` 更新设计/计划并取得必要确认。不要以代码已经写了一半为理由继续。
