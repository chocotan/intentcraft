# 实施与代码审查的共同验证依据

本文件仅定义证据标准，不启动 `ic-do`、不授权执行。实施和审查采用同一标准，但执行权限仍由各自阶段、当前任务与宿主约束决定；审查读到本文件不获得实施或修改被审材料的权限。

## 1. 从验收选择必要检查

用户已确认的要求与项目检查优先；按真实变化和风险补充，不为每个任务套满工具表。用户明确调整要求须记录，不得将未执行项写成通过。

| 变化 | 必要证据 |
|---|---|
| 纯文案、说明或等价小改 | 相关静态/内容检查；不凭空引入测试框架，影响布局或可用操作时仍做浏览器/视觉检查 |
| 分支、解析、计算、状态或错误处理 | 经真实接口执行的回归检查，预期来自需求或独立样例，不复制实现算法当断言 |
| API、数据库、鉴权、跨模块流程 | 按风险做集成验证，优先测试环境真实依赖；覆盖关键约束、失败与恢复 |
| UI 功能 | 浏览器自动化走关键用户旅程及适用的成功、失败、加载、空、禁用、执行中、重试状态；检查键盘、焦点和相关视口 |
| 性能或兼容性主张 | 指定版本、环境、负载/浏览器和方法的实际测量或运行观察；静态推断不是性能数据 |

修 bug 先捕获报告的具体症状，再验证修复与相关边界；无法复现则公开尝试和缺口，不宣称已证实。沿用项目测试体系，小而能捕获回归优于大量重复断言。

## 2. 明确真实与模拟的边界

- 需要时用边界替身或网络模拟复现慢请求、错误、空数据、竞态等，但说明哪些后端/存储契约没有覆盖。
- 模拟 API 成功不证明真实服务集成；截图只证明被捕获状态，不证明整条功能路径。手测、截图和扫描可补充，不能代替必要自动化。
- 在授权测试环境操作，不用生产账户或真实私有数据做破坏性实验；不要将认证文件、秘密凭据和未脱敏日志打包进报告。
- 启动或借用浏览器、dev server、容器和测试数据库前明确资源负责人、使用者和停止条件；只清理自己负责且不再需要的资源，不因本任务结束而关闭他人的服务。
- 工具或环境不足时，区分“未尝试”“实际失败”“无法覆盖”。实施授权内的常规验证应真实尝试；审查阶段未获相应授权时不擅自运行。

## 3. 证据绑定被测内容

每组重要证据包含：目标/场景、实际命令或操作、环境、被测内容标识、结果、日志/截图路径和覆盖限制。

- 干净已提交工作区可记录 commit；有未提交、暂存或相关未跟踪内容时，记录可比对的 diff 或文件内容哈希。仅有 HEAD 或文件名列表不够。
- 相关修改后重跑受影响检查，再运行项目要求的适用完整检查。旧证据只能证明旧内容，不靠新时间戳使它“重新有效”。
- 测试输出、源码测试定义、构建通过、运行观察、用户接受分别记录，不相互替代。
- 主会话整合子任务证据并核对当前版本；子代理只交自己实际执行的结果，不替其他模块或阶段宣称通过。

## 4. 检查、修复与停止

- 先解决任务阻塞、数据风险和不可访问路径，再解决相关状态、兼容与视觉缺陷。
- 视觉打磨可采用有限轮次，不凑问题数量；轮次限制不豁免功能缺陷或必要验证失败。无法继续时报告阻塞和下一步，不无限重复失败命令。
- 扫描命中须核实误报和有意例外；扫描干净不是美观、正确性或安全性的证明。
- 对无关平台/场景的检查可标不适用并给理由；没有运行条件的必要检查应标未验证，不能以不适用掩盖。

## 5. 完成判定与归档

- `implemented-unverified`：已实现，但必要验证尚未完成。
- `verified`：当前目标的必要验证对应当前内容且通过，无已知阻塞缺陷；不表示用户接受或发布授权。
- `blocked`：推进依赖尚未获得的条件，记录已尝试内容、实际错误和最小所需输入。

执行/审查记录进入各自阶段主文档，日志与截图等附件放同主题目录并使用相对链接。主会话维护主文档；子代理只返回正文时由主会话落盘，附件写入还须满足角色边界和明确分配，不相互覆盖。准备/源码/测试条件改变时复查结论，不能只勾掉旧问题。

此规范不要求为 Skill 提示词建立测试套件。配置解析、引用检查和分发检查仅能证明相应静态性质；模型是否遵守角色与流程，要由实际授权会话验证。
