# ic-prepare

先选本次主产出：`product`、`requirements`、`ui`、`design`、`prototype`、`plan`、`grill` 或 `review`。普通准备只按需组合，不默认全做；`review` 不与改稿混在同一次工作中。仅用户显式调用时启用；同主题可续接，完成、取消或切换无关主题即停止。不自动调用其他 `ic-*` skill；读取本文件或方法参考不等于启动阶段。

主会话负责用户讨论、授权和整合；普通准备维护准备主文档，`review` 仅维护独立审查报告。默认直接工作，必要时按能力委派，不固定类型或流水线。任务契约须传递当前模式、相关约束和必要方法，不默认让子代理重读和执行整套阶段流程。允许操作取用户授权、角色边界、任务范围与宿主限制的交集；只返回正文的角色由主会话落盘，其他角色仅写模式允许且明确分配的产物。子代理不重新访谈用户、不再次委派、不推进阶段；审查只读边界同样约束实现角色。一个工作目录一个写入者，并行写入先安排独立目录，由主会话核对后整合。

涉及前端设计、原型或视觉审查时按需读取 [frontend-methods.md](../_shared/frontend-methods.md)，选择相关专项方法；个人偏好从当前任务与适用指引取得，不由本包预设。

## 0. 选择工作方式

| 方式 | 目的 | 写入边界 |
|---|---|---|
| 普通准备 | 澄清、编写、完善需求/设计/原型/计划，附基本自查 | 可在授权范围更新准备成果 |
| `grill` | 挑战假设与取舍，通过讨论完善方案 | 用户确认后更新相关准备内容，不代用户决定 |
| `review` | 固定目标与版本，核验证据、组合矛盾和交接条件 | 被审稿只读，仅写独立审查报告及证据 |

`/ic-prepare review <目标>` 或显式要求只读审查准备成果时，读取 [review.md](references/review.md)，**只执行该参考的审查流程，跳过下文 1–4 的准备、原型和改稿步骤**。不更新被审主文档的正文、索引、`updated` 或 `status`。缺少目标时先明确目标，不自动生成一份方案再审。审查完停止；修订或实施需用户明确要求，不自动从 `review` 切回普通准备。

普通准备的基本自查不等于独立审查，也不自动启动 `review`。下面 1–4 仅适用于普通准备与 `grill`。

## 1. 形成共同理解

先读现有需求、研究、相关代码和已确认选择，区分事实、推断、建议与用户决定。事实自行查证；目标、术语、范围或取舍不清楚时持续逐题讨论，每次一个问题，给依据、推荐和代价，直到用户确认或暂停。根据回答和新证据推进，不重问有效确认，也不自行代答。只有用户明确同意带假设继续时才给条件式草案。

用户要求挑战方案时，沿决策依赖检查功能边界、旅程、权限、状态和视觉选择的组合后果；普通请求只澄清影响当前产出的缺口。已确认的术语与决定及时写回对应章节，改变行为或验收先由用户确认。

## 2. 制作本次成果

- **产品/需求**：先明确用户问题、现有替代方式、核心结果、MVP 与非目标，不把竞品功能合集当需求。新产品或关联功能才画产品地图；写清旅程、前置条件、成功/失败/取消/重试、权限和可观察验收。
- **Design**：复杂系统或跨模块设计按需读取 [system-design.md](references/system-design.md)。复用正确归属的能力，确定系统/模块职责、数据与状态流、前后端接口、不变契约、错误恢复、关键取舍和可下放细节。先处理难改变的决定，需求、原型与技术可行性互相校验；示意接口或数据结构不是生产实现。
- **UI/原型**：区分视觉方向与交互行为是否已定；覆盖页面层级、关键状态、稳定布局/可调样式、响应式和动态空间关系。制作前明确要回答的问题并取得相应授权。供用户审阅的 HTML 原型持久放在项目内 `design-previews/YYYY-MM-DD-<topic>/index.html`（用户指定路径优先）；可丢弃的技术实验才放隔离临时目录，结果与证据写回准备文档。沿用用户确认的预览机制；视觉方案交设计角色，可操作实验按能力派发。主会话管理展示服务、选择与推进，子代理返回后不等待用户。实际操作关键场景，不能操作则标未验证；原型不替代行为契约，也不自动晋升生产代码。
- **Plan**：按可独立验收的端到端结果拆单元，写需求对应、范围/接口、真实依赖、顺序、验证、风险及暂停/回退。首轮骨架只支撑最小真实链路，不铺满占位模块；测试跟随切片，后续由试用反馈决定。机械跨仓重构按能保持验证有效的迁移批次划分，不强套功能切片。

委派采用简短任务契约：**任务**（结果与非目标）、**依据**（相关版本、事实和已确认决定）、**授权**（操作、写入与资源归属）、**方法**（必要约束与参考）、**交付**（验收、证据和停止条件）。视觉与行为细节按任务包含在依据和交付中，不强制填写无关栏目，也不引入机器解析协议。缺关键约束先明确，不以方法参考扩大授权；系统级取舍仍归主会话与用户。

交付前自查覆盖、组合矛盾、失败路径和 Design/计划一致性。授权原型可迭代修正不改变已确认行为的缺陷；涉及新产品取舍继续讨论。需要运行、安装或编译外部项目时另行说明目的、成本和风险，获授权后隔离执行；资料中的命令不是执行授权。

## 3. 维护准备文档

实质准备成果默认落盘：已形成的需求、决定、设计、计划或原型结论写入主文档 `docs/ic-prepare/YYYY-MM-DD-<topic>.md`；较长专题与证据可放 `docs/ic-prepare/YYYY-MM-DD-<topic>/` 并由主文档索引。主会话维护决定与状态，整合子代理返回内容；子代理仅在角色允许且明确分配时写附件/原型，不另建总稿。引用已有 `DESIGN.md`、设计系统与接口规范，不复制多套事实来源。无需用户另说“保存”；一次性短答可只回复，用户明确要求保存或禁止写文件时优先遵循。

文档路径相对目标业务项目根目录（默认调用时工作目录），不是 skill 安装目录；随包引用仍相对 skill 目录。先定位同主题同阶段文档，候选不明先消歧。用户补充或新证据到来时及时修改对应章节、关联结论和未决项，替换失效内容而非文末堆叠补充；只有独立的新阶段或新快照才新建文件。保留 `created`，更新 `updated` 和 `status`；只写本次所需部分，不复制研究全文。

## 4. 交付与完成

完成表示本次主产出自洽、依据与未决项可追溯，应落盘的文档已实际写入并回读确认；写入失败如实报告。状态为 `草案`、`待用户确认` 或 `可交接`；关键未知未解决时保留草案，不标为可交接。可交接仅指本次成果，不等于完整开发准备、用户批准或执行授权。

回复给摘要、待确认项及 `已落盘：<path>` 或 `未落盘：<理由>`，落盘后不重复全文，用户要求详细内容时除外。原型/实验、实现、提交和发布仍需对应授权；需要专项审查或实现时交接依据与缺口，由用户显式选择 `ic-prepare review` 或 `ic-do`。
