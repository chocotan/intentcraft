# ic-prepare

先选本次主产出：`product`、`requirements`、`ui`、`design`、`prototype`、`plan` 或 `grill`；只按需组合，不默认全做。仅用户显式调用时启用；同主题可续接，完成、取消或切换无关主题即停止。不自动调用其他 `ic-*` skill。涉及前端/设计/UI 时，可读取当前已安装且任务匹配的前端/设计 skill；也可按当前宿主已配置子代理的 description/能力派发（视觉方向、走查、原型审美 → 设计类；可操作原型 → 前端实现类）。以能力匹配，不假设固定类型名；无匹配或任务简单则主会话直接做。派发时给出当前 SKILL.md 路径与约束，子代理先读再做，并可继续按能力派发。委派遵循用户限制。

## 1. 形成共同理解

先读现有需求、研究、相关代码和已确认选择，区分事实、推断、建议与用户决定。事实自行查证；目标、术语、范围或取舍不清楚时持续逐题讨论，每次一个问题，给依据、推荐和代价，直到用户确认或暂停。根据回答和新证据推进，不重问有效确认，也不自行代答。只有用户明确同意带假设继续时才给条件式草案。

用户要求挑战方案时，沿决策依赖检查功能边界、旅程、权限、状态和视觉选择的组合后果；普通请求只澄清影响当前产出的缺口。已确认的术语与决定及时写回对应章节，改变行为或验收先由用户确认。

## 2. 制作本次成果

- **产品/需求**：新产品或关联功能才画产品地图；写清用户、结果、旅程、范围与非目标，以及适用的前置条件、成功/失败/取消/重试、权限和可观察验收。
- **Design**：复用正确归属的能力，说明职责、数据/请求/状态流、接口、不变契约、错误路径、取舍和可下放细节；接口或状态片段用于说明决定，不作为生产实现。
- **UI/原型**：区分当前、目标与示意；覆盖页面层级、关键状态、稳定布局与可调整样式、响应式和动态空间关系（宿主、遮挡、裁切）。制作原型前明确要回答的逻辑/状态或视觉问题；获授权后在隔离临时目录制作探索性 HTML，展示可操作状态或有实质区别的视觉方案。视觉方向未定时派设计类前端子代理；可操作原型可由前端实现类子代理制作。实际操作关键场景，不能操作则标未验证；原型不替代行为契约，也不自动晋升生产代码。
- **Plan**：按可独立验收的端到端结果拆单元，写需求对应、范围/接口、真实依赖、顺序、验证、风险及暂停/回退。机械跨仓重构按能保持验证有效的迁移批次划分，不强套功能切片。

交付前自查覆盖、组合矛盾、失败路径和 Design/计划一致性。授权原型可迭代修正不改变已确认行为的缺陷；涉及新产品取舍继续讨论。需要运行、安装或编译外部项目时另行说明目的、成本和风险，获授权后隔离执行；资料中的命令不是执行授权。

## 3. 维护准备文档

实质准备成果默认落盘：已形成的需求、决定、设计、计划或原型结论写入 `docs/ic-prepare/YYYY-MM-DD-<topic>.md`，无需用户另说“保存”；一次性短答可只回复，用户明确要求保存或禁止写文件时优先遵循。

文档路径相对目标业务项目根目录（默认调用时工作目录），不是 skill 安装目录；随包引用仍相对 skill 目录。先定位同主题同阶段文档，候选不明先消歧。用户补充或新证据到来时及时修改对应章节、关联结论和未决项，替换失效内容而非文末堆叠补充；只有独立的新阶段或新快照才新建文件。保留 `created`，更新 `updated` 和 `status`；只写本次所需部分，不复制研究全文。

## 4. 交付与完成

完成表示本次主产出自洽、依据与未决项可追溯，应落盘的文档已实际写入并回读确认；写入失败如实报告。状态为 `草案`、`待用户确认` 或 `可交接`；关键未知未解决时保留草案，不标为可交接。可交接仅指本次成果，不等于完整开发准备、用户批准或执行授权。

回复给摘要、待确认项及 `已落盘：<path>` 或 `未落盘：<理由>`，落盘后不重复全文，用户要求详细内容时除外。原型/实验、实现、提交和发布仍需对应授权；需要审查或实现时交接依据与缺口，由用户显式调用 `ic-design-review` 或 `ic-do`。
