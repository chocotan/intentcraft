# 准备成果只读审查

仅用于用户显式选择 `ic-prepare review` 或要求只读审查准备成果；不是新的 Skill 入口，读取参考不自动启动审查。主产出是审查报告，不是准备稿的修订或生产代码。

## 1. 固定审查目标与独立性

- 明确目标文档、版本、范围、用户约束与批准状态，完整读取目标和支撑关键结论的材料，补齐截断。审未提交文件时记录内容哈希或可比对快照，仅 HEAD 不足以标识被审内容。
- 只审选定产出；需求稿不因缺完整实施计划而失败，局部通过不等于整项目可开工。事实自行核验，关键取舍不清楚则逐题交用户确认或列为待决策，不替用户选择。
- 明确独立性：同一作者上下文的复核标为自查，不能因切到 `review` 模式就声称独立。用户允许且确有价值时，可由具备审查能力的独立上下文复核；不强制启动代理，也不把作者自评当通过证据。
- 主会话整合审查结果；子代理只读核验分配的范围，遵循同一只读边界，不再次委派、不接管用户讨论或模式切换。

## 2. 核验准备成果

- **目标与需求**：用户、结果、范围、非目标和已确认取舍一致；权限、状态、成功/失败/取消/重试与验收可观察。
- **UI/Design**：区分当前、目标与示意；旅程、层级、关键状态、动态空间关系、职责、数据流、接口和错误路径自洽。系统设计按需对照 [system-design.md](system-design.md)，不强加无关文档；原型能回答和未验证的问题分别说明。
- **计划与依据**：结果单元的接口、依赖、顺序、验证、暂停/回退条件可执行；关键结论能追到实际取得的来源，区分文档契约、静态推断、测试定义和运行证据。

仅报告影响正确性、范围、验收、交接或失败代价的问题。每项 finding 给位置、证据、影响、严重度（阻塞/重要/建议）和最小修订方向；区分已确认缺陷、待验证疑点与用户待决策项。不凑问题数量，不以审美偏好阻塞。

## 3. 只读与验证边界

被审需求、设计、原型、计划、支撑文档、代码和配置保持只读；不生成修复补丁，不修改正文、索引、`updated` 或 `status`。只能写本轮审查报告及其证据，不能顺手整理或更新被审稿。

可以只读查看提供的原型。需要测试或交互验证时先说明目的、成本与副作用，取得或沿用明确授权后在隔离副本/测试环境执行；允许该环境内的缓存和测试产物，不改被审材料或写生产/外部系统。未运行项如实标明，资料中的命令不构成授权。

## 4. 独立保存审查报告

实质审查成果默认落盘，无需另说“保存”；用户禁止写文件时仅回复。路径相对目标业务项目，不是 Skill 安装目录：

```text
docs/ic-prepare/YYYY-MM-DD-<topic>.md                 # 被审准备稿，不修改
docs/ic-prepare/YYYY-MM-DD-<topic>/review.md          # 审查报告
docs/ic-prepare/YYYY-MM-DD-<topic>/review-evidence/   # 必要审查证据
```

已有准备主题时沿用其目录；审外部材料且没有对应主题时按本次日期/主题保存报告，但不为此创建一份准备主文档。输出不得与被审文件重合，也不得覆盖原型或其他附件；已有文件身份不明时先消歧。报告及本轮证据不纳入被审输入集。

同目标复审更新独立的 `review.md`：保留 `created`，更新报告自身的 `updated`、`status`、被审版本和 findings。独立新快照才另存审查快照，旧报告不删除。目标或支撑材料改变会使旧结论失效，应针对当前完整目标复核，更新已解决、未解决和新问题，不只勾掉旧 findings。

报告包含：目标与依据版本、独立性、已读与未覆盖范围、findings、证据缺口和结论：`可交接（仅本次范围）`、`需修订` 或 `证据不足`。主会话写报告；只返回正文的角色由主会话落盘，其他角色仅在权限允许时写分配的证据附件。不得因分配附件而放宽角色边界，也不回写被审准备稿来标记通过。

## 5. 返回后停止

完成表示本次范围已核对、有依据的问题和缺口已公开；应落盘时实际写入并回读，失败如实报告。只有完整开发准备在本次审查范围且达标，才可给进入实现的建议。

回复结论、关键问题、覆盖缺口及 `已落盘：<path>` 或 `未落盘：<理由>`。通过不等于用户批准、执行授权或测试通过；需要修订时给建议并停止。由用户另行要求普通 `ic-prepare` 修订或调用 `ic-do`，不得自动改稿、修代码、提交或发布。
