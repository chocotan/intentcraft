# 系统设计与可行性

这是 `ic-prepare` 的方法参考，不启动阶段、不授权生产实现。复杂新功能、跨模块契约或高风险技术决策时使用；简单修复不强制产出架构图和全套文档。总体决定由主会话与用户确认，子代理只提交受派分析或实验结果。

## 1. 从任务与约束出发

- 先明确用户、核心结果、MVP、非目标、既有系统和真实内容范围；竞品机制只是候选，不是已批准需求。
- 识别真正影响方案的性能/容量、延迟、离线/同步、一致性、安全、隐私、部署、成本与维护约束。数字需有来源或标待验证，不凭空许诺 SLA。
- 区分必须现在确定的高代价决定与可下放的可逆细节；只比较有实际意义的替代方案，不强制凑三套架构。

## 2. 明确边界与契约

按本次范围回答下列相关项，不适用说明原因，不为了填写清单创造模块：

| 维度 | 需要确定的内容 |
|---|---|
| 系统与模块 | 外部依赖、前后端职责、模块所有权和调用方向；复用什么，新增什么，为什么不是更简单的结构 |
| 接口 | 输入/输出、版本与兼容条件、错误、鉴权、幂等/重试/取消；避免前后端各自发明语义 |
| 数据 | 核心实体、关系、类型/schema、标识和不变量，数据生命周期、持久化、索引和迁移/回退 |
| 状态与一致性 | URL/服务端缓存/草稿/局部 UI 的归属，同步、竞态、冲突、乐观更新和恢复策略 |
| 安全与权限 | 信任边界、服务端校验、访问控制、敏感数据与外部操作；前端隐藏不替代权限 |
| 运行与维护 | 目标环境、必要依赖、配置和密钥管理、可观测性、故障定位、部署与回退条件 |
| 验证 | 各关键契约如何测试、需要哪些真实依赖、哪些假设尚未证实 |

只有表达关系更清楚时才加模块图、时序图、ER 图或状态图。示意必须标明，不将示例接口/数据结构冒充现有实现。

## 3. 原型、架构与技术选择互相校验

- 交互原型发现撤销、草稿、离线等需求时回查数据与状态设计；技术约束影响交互时回查体验，不等开发完才报告矛盾。
- 栈与库选择依据需求、现有能力、团队/部署成本和可验证约束，不先固定工具箱再反推产品。
- 高风险未知先定义一个有通过/失败条件的最小实验。外部项目安装/执行需相应授权，明确范围与清理方式；实验不自动成为生产骨架。
- 展示原型保存在项目内可重复审阅的位置；技术实验可在隔离临时目录。结论、命令、版本与证据索引进入准备文档，不能只留下将被清理的路径。

## 4. 形成可交接决定

每项重要决定只需写清：问题与约束、选择、关键替代及不选理由、代价/风险、证据或待验证条件、什么变化会推翻它。复用项目已有设计和决策记录，不强制额外创建 ADR 系统。

准备阶段主文档承载已确认决定、范围和状态；较长的接口/数据专题放同主题附件，并引用已有 `DESIGN.md`、设计系统或协议文档，不保存互相漂移的副本。

设计交接说明必须保持什么、哪些可自行调整、关键失败/恢复、接口与数据语义，以及尚未解决的阻塞。具体委派遵循阶段入口的任务契约，不另建一套通用模板；系统级决定不默认交给前端角色。

## 5. 计划按真实结果切片

- 首个切片尽快打通真实入口 → 核心操作 → 服务处理 → 数据保存 → 页面反馈 → 再次打开；只有静态产品时不强加后端或数据库。
- 先搭验证这个切片所需的最小骨架、环境和检查，不预建全部模块与占位接口。
- 每个后续单元写清对应需求、边界/依赖、可观察结果、验证和暂停/回退条件；机械迁移按保持验证有效的批次安排，不硬套用户功能。
- 实现、测试、体验复核围绕每个切片进行；用户试用结果决定下一轮。功能正确、视觉通过与产品有价值是不同结论。

关键未知未解决时，保留草案并列出最小所需证据或取舍；局部可交接不等于整产品已批准开工。
