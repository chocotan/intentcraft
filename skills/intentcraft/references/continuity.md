# 记录、恢复与变更

## 一个事实，一个归宿

沿用项目已有规格、PRD、RFC 或计划。没有归宿且确需建档时，建议在项目文档
目录保存一份 `<topic>.md`，分开需求内容和计划内容；用户指定位置优先。
不要为了安装本 skill 创建目录树。普通短讨论无需文件；用户要求保存或跨会话
需要时取得写入授权，保留最小检查点，不存聊天转录和工具输出全集。

研究过长才拆 evidence 文件，原型另存并引用。已有 PRD 与计划分开时继续分开，
计划引用需求而不另抄一份；不迁移旧档案来适应本工具。

## 最小持久记录
<!-- rule: decision-continuity -->

按需保存：

- 当前问题、目标与范围；重要事实与证据指针。
- 需求与验收、关键选择及理由、未决问题及依赖。
- 已有技术方案、计划单元及引用关系。
- 检查点：当前在解决什么、阻塞、下一步、采用的版本和用户授权范围。

用户批准时记录批准的具体范围与版本，不能由 agent 自己补一个“已批准”。
用已有 Git revision 或内容 hash 标识关键依据；记录 hash 不必提交文件，更不
自动授权 commit。无版本工具时明确记录具体快照，无法确认批准范围就暂停执行交接。
文档就绪、用户批准和执行进度分开；没有跨会话执行需求，不新增执行游标系统。

主题文档不能只记录自己的 hash 而忽略被引用 PRD、关键原型或架构的变化。
只有会影响承诺的外部依据需要版本锚定，不对每个文件建依赖数据库。

## 恢复

先读用户指定主题与必要证据，核对当前版本、未决问题及授权；唯一明确匹配则
继续，不重复询问“要不要继续”。多个候选才消歧，不按最新日期擅自选一个。
发现缺失证据、版本冲突或无法确认批准范围时说明限制；不得把过期检查点当授权。
停止后只有用户显式重新启用 skill 才恢复；本次尚未结束的同主题“继续”不算新启动。

## 变更影响
<!-- rule: invalidate-affected -->

区分实现偏差、局部调整、产品契约变化。按“必须修改 / 需要复核 / 尚待调查”
列出影响。新证据推翻前提时重开该问题，依赖它的选择、计划和旧证据不再默认有效。

- 局部文字/间距调整不推倒架构。
- 角色、权限、状态或验收变化，复核相关需求、原型、方案与验证。
- 无法判定影响范围时先调查，不能默认没有影响。
- 用户尚未选择时保留变更提案，不能先改已批准正文再假装仍可执行。
- 决定后原位更新当前有效正文和引用，清掉矛盾规则；历史交给版本控制。
  不是每轮追加一层“最终修正”让旧结论继续存在。

不自动全部重规划。对受影响部分重新判断需求/计划就绪，未受影响内容保留。
必要的重新批准只针对真实契约变化。只规划不执行时，也不能把待复核计划交给
执行者并标成可开工。
