# 用成果回答问题

先明确“看见或运行什么，才能决定什么”，再选最低充分的形式：文字示例、
状态/时序图、可交互 HTML、接口样例或有界技术实验。不是每个想法都需要原型。

## UI 原型

有用户界面，且未确定的交互/视觉会影响产品结果时才使用。新产品 UI 在正式
实现前需要用户看过并批准，除非明确豁免。纯后端/CLI/库没有这个要求。

标明本轮问题、相关需求、硬约束与模拟部分。覆盖能区分候选方案的旅程及必要
空/加载/失败/权限状态，不为了“一套完整原型”制作所有页面。
使用宿主已有浏览器、设计与评审能力；工具不可用时说明只能给静态草案或操作
说明，不能声称用户已经看过、交互已经验证。仅提供文件路径不等于用户已审阅。

记录用户选择、拒绝项、原因、原型版本和需求影响。修改后的选择需要相应确认，
不能用旧截图的批准覆盖新流程。原型不自动批准数据模型、开发范围或发布。

## 技术实验

后端可能需要实验，但不是 UI 原型：例如验证真实队列重试、鉴权、协议兼容性。
先说明假设、最小操作、通过/失败判据和可能副作用。执行权限不足时只写实验方案。
不要 mock 掉本次要证明的环节；无法接触真实依赖时诚实限定结论。
探索代码保存在隔离的临时/原型位置，不混入生产实现，不自动安装或发布。
复用探索代码需要明确转入实现并重新验证，不能因实验成功就宣称功能已完成。

## 授权后的原型自审与迭代
<!-- rule: prototype-self-review-loop -->

原型产出后，AI 可根据原型复杂度、未决需求和发现风险自行决定是否启动这个闭环；
用户明确要求自行 review 并迭代时必须执行。这个闭环允许检查和修改探索原型，但不等于
用户批准了需求、全部流程、开发范围或发布；新产品在正式实现前仍需用户看过并批准，
除非用户另行明确豁免。

每一轮都实际打开/操作原型（可用时使用浏览器或图像查看工具），再按两层检查：

1. **需求合理性**：目标用户、场景、核心任务、成功标准、约束和非目标是否彼此一致；
   原型是否暴露出不必要的流程、遗漏的空/加载/失败/权限状态、无法解释的概念或把
   未确认的假设写成事实。
2. **原型 review 结果合理性**：对每条 review finding 回到具体需求、用户旅程、页面状态
   或交互证据核对；区分真实缺陷、偏好建议、超出范围的问题和需要用户决定的取舍。
   不因为 review 说“更漂亮/更像某产品”就自动修改，也不把 review 自身当作需求事实。

对确认成立且不改变产品方向的 finding，直接做最小迭代；对会改变目标、权限、关键
流程、范围或验收的 finding，停止自动修改并只问一个取舍问题。每次迭代增加版本号，
记录：原型版本、检查的需求/旅程、finding、finding 是否成立及依据、修改内容、仍未
验证项和需求影响。修改需求后同步复核受影响的原型与计划，不能用旧版本结论覆盖新版本。

当关键需求问题已澄清、连续检查没有会影响选择的新 finding，或下一步必须由用户选择
时停止；交付当前版本和未决项。自审循环不调用独立 review skill，不把“自审通过”写成
用户验收或运行验证。

## 反馈闭环

文字可以解释的就解释；需要操作判断的就给成果；事实未知的就调查。每次只处理
会影响当前选择的反馈。若用户改变了目标而不是回答原问题，停止继续打磨原型，
按 [记录与变更](continuity.md) 更新受影响的需求和计划。
