# 把需求变成可交接计划

先读取当前有效需求与其重要证据。缺少产品行为时回到讨论；已经足够明确则
直接规划，不强制从头研究或先建 PRD。请求是“只出计划”时不暗中写生产代码。

## 先调查，再定结构

修改已有系统前，查清相关能力的归属、调用方、数据/状态、契约、测试和相邻模式。
外部 API 或机制影响方案时，核对实际版本和资料，按 [研究与证据](research.md)
执行；必要实验按 [原型与实验](probes.md) 独立限定范围和授权。

优先复用正确归属的现有能力，其次标准库/原生平台，再考虑已装依赖和新实现。
重要技术选项说明取舍，不强制为显然选择写三套架构；新增复杂度必须服务当前目标。
需要画清组件、状态或跨进程关系时画图，图不代替文字契约；纯后端不需要 UI 图。

## 计划单元是结果，不是两分钟操作
<!-- rule: outcome-units -->

优先安排能尽早暴露真实集成风险的最小端到端路径，之后逐个增加完整能力。
不要“先写所有模型、再写所有接口”直到最后才整合；必要基础设施可作为明确
前置单元，但必须指出它使哪个结果成为可能，以及怎样证明它本身成立。

每个需要交接的单元使用稳定 `U1` 等 ID，说明：

- **目标与需求**：完成后的结果、对应 R-ID。
- **依赖与范围**：前置 U-ID、模块/文件、不得改变的契约。
- **方案与理由**：数据流、模块边界、关键决策、复用的模式。
- **验证场景**：具体输入/状态、动作、预期结果，覆盖适用的成功、异常与集成路径。
- **未知与回退**：实现者可以自行决定什么，出现什么证据必须重新讨论。

重要的共享接口写到不会让不同实现者猜出冲突契约；已知符号可准确引用，新路径
标成拟新增。局部 helper 名和完整实现代码不必预写。文件路径用项目相对路径，
优先路径+符号而不是易失效的行号。别用“加适当校验”“写充分测试”充当方案。

已知权威测试命令可以记录，并说明它证明什么；未运行就标为计划，不能编造运行
结果。需要人工体验或外部设备的检查写明确操作、预期和条件，不伪造一个 grep 命令。

## 双向覆盖与未知

从每条需求找到对应单元/验收或用户确认的暂缓项；从每个单元反查需求或必要
技术依据，阻止顺便重构和悄悄扩范围。单位顺序改变不重编号。

- 能由源码和文档查清：规划阶段调查。
- 必须运行才能知道：安排明确的实验或实施时检查。
- 会改变产品范围、安全或关键架构：先解决或保留阻塞，不能交给实现者猜。
- 不影响承诺的局部细节：显式下放，不为“完整”制造假确定性。

## 就绪与交接
<!-- rule: plan-ready -->

计划可交接需要：需求和引用版本有效、关键方案有依据、单元与依赖清楚、验证
具体、重要未决阻塞已解除。可交接不等于已验证，更不等于用户授权执行。

检查本次是否改变需求原意、遗漏限定条件、引入相互矛盾的设计。实质变化回到
用户选择；局部技术细化在批准边界内完成，不重复问已经明确的产品选择。
已有计划要求深化时，只补薄弱的依据/方案/覆盖，不用重写整份文档制造工作量。
